# Android 应用技术分析报告 — `com.cnvcs.junqi` v1.58

> 目标样本：`base.apk`（8.50 MiB）
> SHA-256：`3cb1aae814be03d23ce452b047e630d422c01ee154811d2578973ba1d2202426`
> 分析方式：全静态离线分析（授权依据：本地自有样本，`scope.md` → `auth.status = granted`）
> 工具链：jadx 1.5.6 + apktool 3.0.2 + 自研 Python 侦察脚本（ELF / ZIP / DEX 解析）
> 日期：2026-09-10

---

## 1. 结论摘要（TL;DR）

1. **样本未加壳**，可完整静态分析。`classes.dex` 仅 1 个，1,224 个类 / 12,788 个方法，规模很小。
2. **Java 层源码已 100% 还原**：apktool 解出 1,223 个 smali（500 顶层类 + 723 内部类），jadx 对应产出 501 个 `.java`（500 顶层 + 1），反编译错误数 **0**，共 81,876 行 / 71 个包。
3. **但这个 App 的"源码"有天然边界**：它本质是一个 **JNI + OpenGL ES 的壳**。唯一的 Activity `com.cnvcs.App` 只有 136 行，声明了 15 个 `native` 方法，`System.loadLibrary("junqi")` 把全部业务逻辑交给 `libjunqi.so`（ARM 32 位，1.25 MiB）。**军棋的对局规则、AI、网络协议都在原生库里，不在 Java 层。**
4. **Java 层实际内容 = 自有 UI 壳（1,483 行）+ 广点通广告 SDK（148 类）+ Android support/androidx 库（343 类）**。自有代码只有 9 个类。
5. **未发现恶意行为**：无动态代码加载、无命令执行、无设备指纹采集（自有代码中 `getDeviceId` / `Cipher` / `exec` 命中数均为 0）；native 库无任何 URL/域名、无 `ptrace`/`TracerPid`/反 Frida 等反调试特征。广告 SDK 是唯一的网络出口。
6. 存在若干**低风险但值得记录的配置问题**：`usesCleartextTraffic=true`、`allowBackup=true`、`targetSdkVersion=26`、申请 `READ_PHONE_STATE` / `QUERY_ALL_PACKAGES` / `REQUEST_INSTALL_PACKAGES`。
7. 资源被封装在自研 **SPAK** 分片容器中（`assets/data*.pak` 等 8 个文件），按 1,000,000 字节切片，只有第 0 片带 magic。

**要拿到"真正的完整源码"（含军棋规则与 AI），下一步必须对 `libjunqi.so` 做原生反编译**（Ghidra 无头模式或 IDA Pro）。本报告第 6 节给出可行路径。

### 3.1 样本指纹

| 包名 | `com.cnvcs.junqi` |
| 版本 | versionCode **158** / versionName **1.58** |

| APK 大小 | 8,908,897 字节 |
| ZIP 条目 / 解压后 | 176 / 10,382,909 字节 |

| 签名 | `META-INF/CERT.RSA`（661 B，SHA-256 前缀 `3c66a205…`） |

### 3.2 代码构成

| 包 | .java 文件 | 性质 |
|---|---|---|
| `android.*`（含 `android.support.*`、`android.arch.*`） | 334 | Android 旧版 support 库（被 repackage 进 `android` 包） |

| **合计** | **501** | 81,876 行 / 71 个包 |

### 3.3 Manifest 要点

- **唯一 Activity**：`com.cnvcs.App`（`portrait` 固定竖屏，`Theme.Black.NoTitleBar`，`resizeableActivity=false`），带 `MAIN`/`LAUNCHER`。
- **Provider**：`com.cnvcs.ShareProvider`（`exported=false`，`grantUriPermissions=true`）、`com.qq.e.comm.GDTFileProvider`。
- **广告组件**：`ADActivity` / `PortraitADActivity` / `LandscapeADActivity` / `Rewardvideo*Activity` / `DownloadService`（均 `multiprocess=true`）。
- **meta-data**：`android.max_aspect=2.7`、激励视频 Activity 加 `android.notch_support=true`。
- `BtReceiver` **未在 Manifest 注册**，属运行时动态注册（配合蓝牙对战）。

### 3.4 权限与配置风险

| 项 | 级别 | 说明 |
|---|---|---|
| `android:usesCleartextTraffic="true"` | 低 | 允许明文 HTTP；native 库本身无 URL，风险主要来自广告 SDK 落地页 |
| `android:allowBackup="true"` | 低 | 可 `adb backup` 导出应用数据 |
| `targetSdkVersion=26` | 低 | 远低于当前商店要求（Android 14 起要求 34），老设备兼容模式运行 |
| `READ_PHONE_STATE` | 中 | 敏感权限，广告 SDK 常借此取设备标识；自有代码**未**调用 `TelephonyManager` |
| `QUERY_ALL_PACKAGES` | 中 | 可枚举全部已安装应用，商店政策敏感 |
| `REQUEST_INSTALL_PACKAGES` | 中 | 可触发 APK 安装，配合 GDT `DownloadService`（广告落地页下载） |
| `ACCESS_COARSE_LOCATION` + `BLUETOOTH`/`BLUETOOTH_ADMIN` | 低 | 广告定向 / 蓝牙对战 |

## 4. 核心发现：业务逻辑在 native 层

### 4.1 Java ↔ native 桥接面（F-001）

`com.cnvcs.App` 完整声明如下 15 个 native 方法（`03-native/libjunqi-elf.md` 中导出的 `Java_com_cnvcs_App_*` 符号与之**逐一对应**，证明无 `RegisterNatives` 动态注册绕过）：

| native 方法 | 触发点 | 作用推断 |
|---|---|---|
| `OnCreate(Activity)` → `GLView` | `onCreate` | 创建渲染视图（native 侧 new 出 GLView 并返回） |
| `OnGraphCreate()` | `onSurfaceCreated` | EGL 上下文就绪，初始化渲染资源 |
| `OnGraphChange(w,h)` | `onSurfaceChanged` | 分辨率变化 |
| `OnUpdate()` | `onDrawFrame` | **逐帧主循环**（返回 boolean 控制是否继续） |
| `OnTimer()` | `Handler` 每 **100ms** 一次 | 定时器 / 逻辑心跳 |
| `OnTouch(MotionEvent)` | `onTouch` | 触摸输入 |
| `OnKey(KeyEvent)` | `onKeyDown/Up` | 按键输入 |
| `OnPause()` / `OnResume()` | 生命周期 | 暂停 / 恢复（挂后台判断） |
| `OnDestroy()` | `onDestroy` | 资源释放；**随后 `System.exit(0)` 强制退进程** |
| `OnInput(String)` | `InputDlg` 确定 | 对话框文本回填 |
| `OnResult(int,int,Intent)` | `onActivityResult` | 支付/分享/广告返回 |
| `OnPermission(int,String[],int[])` | `onRequestPermissionsResult` | 动态权限结果 |
| `OnEvent(String,String)` | — | 通用事件通道（键值对） |
| `OnBluetooth(Intent)` | `BtReceiver` | 蓝牙对战数据 |

**含义**：Java 层只是"输入输出适配器"。**军棋的走子规则、悔棋（`Junqi.RegretReq/RegretAgree/RegretDisagree/RegretSend` 等协议字符串出现在 .so 中）、AI、残局、联网协议全部在 `libjunqi.so` 内。**

### 4.2 native 库侦察

| 项 | 结果 |
|---|---|
| 架构 | ELF **32 位 / little-endian / ARM / DYN**（`armeabi-v7a`） |
| 大小 / SHA-256 | 1,308,992 字节 / `700660ab9a80fbaa84c8af791d771a3bf71000bb85708ea6c23af6e60026427a` |
| 可打印字符串 | 21,777 条 |
| JNI 导出 | 15 个 `Java_com_cnvcs_App_*`（静态导出，无动态注册） |
| C++ 修饰符号 | 530 个（`_ZN*`，说明以 C++ 实现，含类/命名空间） |
| 引擎指纹 | **未识别到 Cocos2d-x / Unity / Lua / LayaBox**（`cocos`/`lua_`/`CCDirector` 命中均为 0）→ **自研引擎** |
| 网络行为 | **URL 0 条、域名 0 条**，唯一 IP 字面量是 `255.255.255.255`（广播地址） |
| 反调试 / 反注入 | **均未命中**（无 `ptrace`、`TracerPid`、`ro.debuggable`、`ro.secure`、`frida`、`xposed`、`/proc/self/maps`） |
| 其他 API | `fopen` / `dlopen` / `dlsym` 各 1 次（常规） |

> 注：初版脚本曾把 `Junqi.RegretReq`（悔棋协议）里的 `egret` 子串误判成 Egret 引擎，已改为词边界匹配后复测，确认**无引擎指纹**。同类误报也已从"风险特征"中修正（`su` 曾因 `success`/`result` 子串虚报 40 次）。修正记录见 `scripts/elf_triage.py` 注释。

### 4.3 资源容器 SPAK（E-007）

`assets/` 下 8 个 `.pak` 构成 3 条流：`data*`（1.18 MiB）、`datah*`（1.24 MiB）、`datax*`（3.53 MiB）。

- 仅每组的 **第 0 片**带容器头：magic `SPAK` + `01 00 00 00`（版本 1）+ 一个 32 位长度字段；
- 每条流按 **1,000,000 字节**硬切，后续分片是纯续写（无 magic）：
  `cat data0.pak data1.pak > data.spak` 即可还原单流；
- 头部长度字段比拼接总长小 2,736 / 6,144 / 7,549 字节（差值不恒定，疑为索引区/TOC 长度，**待 native 侧结构体反向确认**）；
- 非第 0 片的内容呈高熵（疑似压缩或加密），需结合 `.so` 中的解包函数才能定论。
