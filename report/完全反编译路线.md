## 1. 为什么「完全」存在硬边界（先说清楚，避免预期错位）

反编译**永远拿不回原始工程**，能拿回的是「功能等价的高级语言表达」。以下信息在编译期被不可逆丢弃：

| 丢失项 | 能否恢复 | 说明 |
|---|---|---|
| 函数边界 / 调用图 / 控制流 | ✅ 可恢复 | 反编译器基本能还原 |
| 字符串、常量表、协议字段名 | ✅ 可恢复 | 本样本全明文，恢复质量很高 |
| 类/方法名（mangled） | 🟡 部分 | 依赖 `.dynsym`；本样本仅 829 个 `_Z*` 且多为 std 库，自有类名已 strip |
| 局部变量名、参数名 | ❌ 不可恢复 | 编译期丢弃，只能按语义猜（反编译器给 `uVar1`/`iVar2`） |
| 注释、宏、模板源码、预处理器 | ❌ 不可恢复 | 编译后不存在 |
| `inline` / 模板实例化的原始边界 | ❌ 不可恢复 | 已被内联展开 |
| 数据表（棋盘规则/评估权重） | ✅ 可恢复 | 通常在 `.rodata` 或 pak 里，属于「数据」不属于「代码」 |

所以本项目的**可达上限**是：
- Java 层 → 完全等价源码 ✅
- Native 层 → 817 个函数的 C 伪代码 + 可读的规则/协议逻辑（人工可读、可改、可重编译），但变量名需推断 ✅
- 资源数据 → pak 解密后完整取出原始 PNG/XML/配置 ✅

**「完全」= 上述三项全绿，而不是「原样拿回 .cpp」。**

## 2. 路线 A：Native 静态反编译（主路径）

### 2.1 工具选择

| 工具 | 成本 | ARM32 反编译 | 建议 |
|---|---|---|---|
| **Ghidra 12.1.3**（headless） | 免费 | 优秀 | ⭐ **首选**，可脚本化批量导出 |
| IDA Pro + Hex-Rays ARM | 商业 | 最好 | 若你已有授权可用，伪代码更干净 |
| Binary Ninja | 商业 | 优秀 | 有 HLIL，批量导出方便 |
| radare2 / rizin (`pdc`) | 免费 | 一般 | 只做辅助校验 |
| RetDec | 免费 | ARM 支持弱 | 不推荐用于本样本 |

**结论：Ghidra headless 足够，且能一键批出 817 个函数的 C 代码。**

环境要求：**JDK ≥ 21**。本机 Android Studio 自带 JBR 25，可直接用；若 Ghidra 12.x 对 JDK 25 报兼容性错误，再补一个 Temurin 21。

### 2.4 符号恢复策略（决定「像不像源码」）

这是把伪代码从「不可读」拉到「可读」的关键，分三档：

1. **`.dynsym` 自动命名** —— Ghidra 导入即生效，829 个 `_Z*` 自动 demangle（多为 `std::` 库，能帮我们过滤掉「不是业务代码」的部分）。
2. **字符串交叉引用自动重命名**（自写脚本）—— 本样本有 **106 条 `Junqi.*` 业务串 + 完整资源路径表**，把「引用该串的函数」自动改名，例如：
   - 引用 `Junqi.RegretReq` → `Msg_RegretReq_Send`
   - 引用 `/data/sg/piece.png,%d,%d,%d,%d,clip` → `Render_Piece_Clip`
   - 引用 `data/config/ui.xml` → `UI_LoadConfig`
   - 引用 `SPAK` → `Pake_Mount` / `Pake_VerifyMagic`
   这一步能把几百个函数从 `FUN_000a8610` 变成有意义的名字。
3. **Function ID (FID) 库匹配** —— 用 Ghidra 官方 FIDB 把 zlib / OpenSSL / libc 等第三方面孔自动识别掉，剩下的就是纯业务代码，人工阅读量骤减。

配合这三档，**实际需要人工精读的函数通常能压到 100～200 个以内**。

## 3. 路线 B：数据容器 SPAK 解密

### 3.1 已破解的容器结构

```
偏移 0x00  "SPAK"                        magic
偏移 0x04  0x00000001                    version = 1
偏移 0x08  1235978 / 1294907 / 3691991   载荷大小 A
偏移 0x0C  2736    / 6144    / 7549      索引大小 B
偏移 0x10  ...加密/压缩载荷...
末尾       B 字节索引（同样加密）
```

**验证**：`A + B == 该组全部分片文件大小之和`，三组全部吻合（data / datah / datax），所以 **B 字节索引固定挂在最后一枚分片的尾部**。

### 3.2 载荷性质判定（已排除的可能）

| 测试 | 结果 | 推论 |
|---|---|---|
| 全局熵 | **7.997**（16 个采样点全部 ≥7.99） | 压缩或加密，二选一 |
| zlib (wbits 15/-15/31/47) @ 6 个起点 | 全部失败 | 不是标准 zlib 流 |
| lzma / bz2 | 全部失败 | 不是标准压缩容器 |
| 索引区（末片尾部）可打印串 | 无可读路径名 | 索引也被同样处理过 |
| `.so` 内 AES S-box / 逆 S-box | **0 命中** | 不是标准 AES 表实现 |
| `.so` 内 TEA/XXTEA delta (0x9E3779B9) | **0 命中** | 不是标准 XXTEA |
| `.so` 内 SHA-256 常量 | 0 命中 | — |

**结论：不是任何标准算法，是自研轻量加解密**（常见形态是按 16/32 字节块做 XOR + 位移的自定义轮函数，密钥可能硬编码或由包名/版本派生）。**这类算法只能靠反编译 `.so` 还原**，纯数据侧爆破性价比极低。

### 3.3 两条可行路径

**路径 B1（静态，推荐）**：在 Ghidra 里定位容器函数 ——
- 搜字符串 `SPAK` 的交叉引用（已定位 `.text` 内约 `@0x0a8610` 附近有 magic 比较序列）；
- 搜 `data/config/ui.xml`、`data/sg/board.png` 等路径模板的引用点，那里就是索引解析函数；
- 还原索引结构（文件名 + 偏移 + 长度 + 原大小）与解密轮函数；
- 用 Python 复刻，一次性解出全部资源。

**路径 B2（动态，更省事）**：MuMu 12 跑起来 + Frida hook 解密函数，直接 dump 解密后的内存/文件。不必理解算法。

## 4. 路线 C：动态验证（MuMu Player 12 + Frida）

本机已装 MuMu Global 12.0（`E:\Software\MuMuPlayerGlobal-12.0`）。价值在于**验证静态结论**，而不是替代静态分析。

```
adb connect 127.0.0.1:7555           # MuMu 12 默认 ADB 端口
frida -U -f com.cnvcs.junqi -l hook.js --no-pause
```

优先 hook 15 个 JNI 入口中的这几个，它们是游戏主循环：

| 入口 | 用途 |
|---|---|
| `Java_com_cnvcs_App_OnCreate` | 初始化，能看到资源挂载、密钥生成 |
| `Java_com_cnvcs_App_OnEvent` | 事件总线，**协议收发主通道**（`Junqi.*` 消息都过这里） |
| `Java_com_cnvcs_App_OnUpdate` / `OnTimer` | 帧循环，AI 落子时机 |
| `Java_com_cnvcs_App_OnGraphCreate` | 渲染资源加载 → **拦这里能拿解密后的贴图** |

样本**未发现反调试**（无 ptrace / TracerPid / frida 检测），动态阻力很低，属于「接上就能跑」。


① 完成即可让 native 层从 0% → 约 70%（结构全在，变量名待推敲）；②③④ 完成可到约 90%；⑤ 用于兜底与验证。
