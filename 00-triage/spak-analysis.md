# SPAK 容器算法分析总报告（最终版 · 已破解）

> 目标：解出 `assets/data*.pak` 内的全部资源。
> 结论：**已完全破解**。SPAK = 24 字节头 + 载荷区 + 索引区，
> 载荷/索引统一采用「32 字节循环异或 + 标准 zlib」，
> 索引条目 = `16 字节目录键 + u32 绝对偏移 + u32 存储长度 + u32 原始长度`。
> 实测 **690/690** 条资源全部成功解密解压（100%）。

## 一、容器结构

```
偏移 0x00  u32 magic       "SPAK" = 0x4B415053
偏移 0x04  u32 version     = 1
偏移 0x08  u32 index_off   索引区在文件中的绝对偏移（== 载荷区结束位置）
偏移 0x0C  u32 index_csize 索引区「压缩+异或」后长度
偏移 0x10  u32 checksum    crc32(索引密文) ^ 0x2713
偏移 0x14  u32 index_raw   索引区解压后长度 = 28 * 条目数
0x18 ~ index_off            载荷区
index_off ~ EOF             索引区
```

| 组 | 分片 | index_off | index_csize | index_raw | 条目数 | 载荷区 |
|---|---|---|---:|---:|---:|---:|
| data  | data0 + data1 | 1,235,978 | 2,736 | 3,416 | **122** | 1,235,954 |
| datah | datah0 + datah1 | 1,294,907 | 6,144 | 7,140 | **255** | 1,294,883 |
| datax | datax0..3 | 3,691,991 | 7,549 | 8,764 | **313** | 3,691,967 |

按 1,000,000 字节切片，仅第 0 片带 24 字节头。三组头部字段、校验、长度全部精确自洽。

## 二、索引条目格式（28 字节）

```
+0x00  16 字节   目录键（见第五节：data 组为 MD5(资源路径)）
+0x10  u32        载荷偏移（**绝对**，从文件头算起，首条 = 0x18）
+0x14  u32        csize（存储长度）
+0x18  u32        usize（原始长度）
```

条目在载荷区**首尾相接**：`off[i+1] == off[i] + csize[i]`（已逐条验证）。

## 三、核心算法（Ghidra 反编译 + 实测校正）

### 3.1 异或（`FUN_000bcb60`）

```c
for (i = 0; i < len; i++) data[i] ^= KEY[i % 32];   // 相位从 0 开始
```

- `KEY` 位于 `.rodata`：虚拟地址 `0x001356d4`（本 .so 中**文件偏移 == 虚拟地址**）。
- **实测密钥（32 字节）**：
  ```
  c2cb e5e7 ce5c 4ac4 11ca 6c99 06f4 76f8
  6d4f cbb6 2621 de0e 6a67 874c 93f0 d523
  ```
- 关键：**异或相位对每条资源从 0 重新开始**（不是整段连续，也不是按分片重启）。

### 3.2 解压（`FUN_000b4638` → `FUN_000ea534` → `FUN_000ea7c4`）

`FUN_000ea7c4` 是 `inflateInit2_` 包装，`version = "1.2.8"`、`windowBits = 0xf`（标准 **zlib** 头，非 raw、非 gzip）。
即：`csize != usize` 时走 `zlib.decompress(...)`。

### 3.3 分发规则（决定性）

| 条件 | 处理 |
|---|---|
| `csize != usize` | 先异或（相位 0），再 **zlib inflate** |
| `csize == usize` | 先异或（相位 0），**原样存储**（PNG / 文本 / 二进制） |

### 3.4 解包伪代码

```python
blob = data0+data1            # 分片顺序拼接
idx  = zlib.decompress(xor(blob[idx_off : idx_off+idx_cs], KEY))
for i in range(idx_raw // 28):
    key16, off, cs, us = unpack("<16sIII", idx[i*28:(i+1)*28])
    plain = xor(blob[off : off+cs], KEY)               # 绝对偏移，相位 0
    data  = zlib.decompress(plain) if cs != us else plain
```

## 四、早期的六项「否定」实验为何全部为假阴性

早期仅做数据侧统计，未读代码，因此把 `csize == usize` 与 `csize != usize` 混在一起、
且按「整段连续异或」假设去扫描 zlib 头，导致：

| 早期假设 | 为何被否定又其实成立 |
|---|---|
| 「无标准压缩流」 | 索引/压缩条目其实**是** zlib，但异或相位**逐条重置**、偏移为**绝对**，全偏移扫描自然全部落空 |
| 「不存在固定周期密钥」 | 周期恰为 32，且被错误地在「整段」上求 gcd 而掩盖 |
| 「变换逐字节位置无关」 | 对：异或确实逐字节独立，这正是能保留 170 字节重复区的原因 |

**教训**：在不掌握调用约定（偏移基准、相位基准、分支条件）时，纯统计结论不可靠。

## 五、目录键语义（资源名恢复）

- `data` 组：目录键 = **MD5(资源路径)**，可逆推。
  已据此恢复 **108/122** 个真实文件名（`data/lay/*.lay`、`data/ad/*.cfg`、
  `data/config/*.xml`、`data/junqi/*.wav`、`data/ui/*`、`data/font/936.cp` 等）。
- `datah` / `datax` 组：目录键**不是** MD5(任何已知路径)。
  已排除：MD5(路径) 各种前缀/后缀/编码/大小写变体、MD5(内容)、数值 ID、
  以组名做前缀、密度后缀（`_h/_x/@2x/hd`）、多语言编码（UTF-8/GBK/UTF-16）。
  两组的键集合与 `data` 组**零交集**，属独立命名空间。
  推断：其资源名由运行期拼装（可能来自服务端下发或引擎内部标签），静态无法穷举。
  这些条目以 `<md5>.<ext>` 命名，并按内容标注类型/尺寸。
